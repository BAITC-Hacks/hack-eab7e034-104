# StockPilot — рекомендации по пополнению склада

Прототип для логистического кейса HackAlem AI 2026 и ТОО «Электрокомплект». StockPilot помогает менеджеру закупа оценить потребность в товарах, увидеть риск дефицита и подготовить список рекомендаций для ручного согласования.

## Проблема и решение

Ручной расчёт в таблицах отнимает время и может скрывать дефицит. Разовая крупная продажа также способна исказить оценку регулярного спроса.

StockPilot объединяет подготовленные данные по ассортименту, продажам, остаткам и товарам в пути. Для каждого SKU приложение показывает прогноз на выбранный горизонт, доступный запас, рекомендуемое количество, срочность и факторы расчёта. Итог проверяет сотрудник закупа; приложение не отправляет заказы поставщикам.

## Что реализовано

- Каталог из 3 906 SKU поставщиков Systeme Electric и IEK.
- Прогноз спроса с календарной сезонностью, взвешиванием более свежих месяцев и затухающим трендом.
- Снижение влияния разовых крупных продаж на регулярный прогноз: анализ крупных документов на уровне SKU и ограничение месячных выбросов.
- Расчёт количества с учётом текущего остатка, товаров в пути, буфера 15% и MOQ (минимальной партии).
- Оценка срочности по покрытию запаса относительно планового горизонта.
- Разбивка рекомендаций по поставщикам; фильтры по поставщику и срочности, поиск по артикулу и наименованию.
- Объяснение по каждой позиции: прогноз, доступный запас, сезонность, тренд, учтённые выбросы, stockout-поправка и MOQ.
- Сценарий «Что если?»: горизонт, изменение спроса, остаток, транзит и stockout-дни для выбранного SKU.
- Загрузка CSV с периодами отсутствия товара и экспорт видимых рекомендаций в CSV.
- Отдельный список SKU, отложенных из-за неполных исходных данных.
- Русскоязычный закупочный агент с локальным demo-режимом и опциональным вызовом OpenAI.

## Как работает решение

1. Приложение загружает агрегированный снимок данных поставщиков на 22 сентября 2026 года.
2. Пользователь выбирает поставщика и горизонт либо вводит запрос агенту, например: «Покажи срочные позиции IEK на 45 дней при росте спроса на 15%».
3. Агент (если подключён OpenAI) извлекает параметры сценария и вызывает расчётный инструмент. Без API-ключа demo-агент распознаёт поставщика, число дней, процент изменения спроса и SKU по простым правилам.
4. Python-модуль прогнозирует спрос, применяет сезонность, тренд и доступные поправки на аномалии/stockout, затем вычитает остаток и товары в пути.
5. Дефицит увеличивается на 15% буфера и округляется вверх до MOQ. Результат сортируется по поставщику и срочности.
6. Закупщик проверяет объяснение, меняет параметры при необходимости и экспортирует список в CSV для дальнейшего согласования.

Количество рассчитывает детерминированный код. OpenAI используется для понимания запроса и текстового объяснения, а не для арифметики.

## Технологии

- **Python 3.10+** — API-сервер и расчётная бизнес-логика.
- **Стандартная библиотека Python** — **http.server**, обработка JSON и gzip, локальные HTTP-запросы к OpenAI.
- **HTML, CSS, JavaScript** — интерфейс без фронтенд-фреймворка.
- **OpenAI Responses API** — опциональный AI-агент с вызовом функции **calculate_replenishment_plan**. Текущая настройка модели по умолчанию: **gpt-5.6-terra**; модель можно изменить через **OPENAI_MODEL**.
- **openpyxl 3.1+** — только для пересборки каталога из исходных XLSX-файлов внутри архивов поставщиков; для обычного запуска не требуется.
- **JSON + gzip** — локальное хранение подготовленного каталога.

В проекте нет базы данных, карты, внешних логистических API, подключения к 1С или сторонней авторизации.

## Архитектура

    Браузер: HTML / CSS / JavaScript
        │ JSON API
        ▼
    app.py: локальный HTTP-сервер, проверка запросов и API-маршруты
        ├── agent.py: OpenAI Responses API или локальный demo-агент
        ├── replenishment.py: прогноз, правила закупки и проверка параметров
        └── data/demo_catalog.json.gz: агрегированный снимок данных
                 │
                 ▼
    Рекомендации и объяснения → интерфейс → CSV для ручной проверки

Основные API-маршруты:

- **GET /api/health** — статус приложения, источники и ограничения данных.
- **GET /api/products** — краткий каталог товаров.
- **POST /api/recommendations** — детерминированный расчёт плана.
- **POST /api/agent** — запрос к закупочному агенту.

Сервер по умолчанию слушает только **127.0.0.1:8000**. Структура репозитория:

    agent.py                    AI-агент и локальный demo-режим
    app.py                      HTTP API и загрузка каталога
    replenishment.py            прогнозирование и расчёт закупки
    data/demo_catalog.json.gz   подготовленный снимок данных
    scripts/build_demo_data.py  сборка каталога из отчётов поставщиков
    frontend/                   веб-интерфейс
    tests/                      unit- и API-smoke-тесты
    docs/data_sources.md         происхождение и обработка данных

## Установка и запуск

Требуется Python 3.10 или новее. Для запуска приложения сторонние Python-пакеты не нужны.

В PowerShell из распакованной папки проекта:

    python --version
    python app.py

Затем откройте в браузере:

    http://127.0.0.1:8000

Остановить сервер можно сочетанием Ctrl+C в окне PowerShell. Каталог уже включён в репозиторий в сжатом виде.

### Опционально: подключить OpenAI

Скопируйте шаблон окружения и добавьте собственный ключ в локальный файл **.env**:

    Copy-Item .env.example .env

В **.env** задаются **OPENAI_API_KEY** и, при необходимости, **OPENAI_MODEL**. Не публикуйте файл **.env** и не добавляйте секреты в Git. Без ключа интерфейс работает в помеченном demo-режиме; при ошибке OpenAI агент переключается на локальный расчёт.

Для реального вызова OpenAI требуется подключение к интернету и действующий API-ключ. В OpenAI отправляется текст запроса и сводка расчёта максимум по десяти верхним рекомендациям, включая SKU, наименование, количество и объяснение. Номера документов и клиентские данные в каталог не включаются.

### Опционально: пересобрать каталог

Исходные архивы поставщиков не входят в репозиторий. Для пересборки подготовленного JSON из доступных команде архивов установите openpyxl и передайте пути к архивам:

    python -m pip install -r requirements.txt
    python scripts/build_demo_data.py --systeme "C:\data\Systeme electric.zip" --iek "C:\data\IEK.zip" --output data/demo_catalog.json

Скрипт сохраняет агрегаты по SKU и месяцу, остатки, транзит и сведения для обработки выбросов; номера документов, описания накладных и отдельные складские строки отбрасываются. При наличии **data/demo_catalog.json** приложение предпочитает его сжатому снимку.

## Как проверить решение

1. Запустите приложение и откройте **http://127.0.0.1:8000**.
2. В панели агента отправьте запрос: «Покажи срочные позиции IEK на 30 дней».
3. Убедитесь, что в ответе есть число рекомендаций и примеры SKU с количеством и обоснованием.
4. Выберите строку в таблице, чтобы увидеть детали прогноза, запаса, транзита и MOQ.
5. Откройте «Что если?», задайте горизонт 45 дней и рост спроса 15%, выберите SKU и увеличьте транзит на 500 единиц. Пересчитайте сценарий и сравните рекомендации.
6. Экспортируйте отображаемые строки в CSV. Экспорт предназначен для просмотра и дальнейшего ручного согласования.

Без **OPENAI_API_KEY** шаг 2 выполняется локальным demo-агентом. Для проверки расчётного API можно запустить тестовый набор:

    python -m unittest discover -s tests -v

## Данные и интеграции

В репозитории находится агрегированный демонстрационный снимок, подготовленный из архивов отчётов Systeme Electric и IEK. Данные включают месячную историю продаж, SKU, наименование, доступные категории и единицы, текущий остаток, сведения о товарах в пути и MOQ, если они были переданы. Дата среза каталога — 22.09.2026. Подробности обработки описаны в [docs/data_sources.md](docs/data_sources.md).

Источники не обновляются автоматически. В текущей версии нет подключения к 1С или постоянного импорта новых файлов. Stockout-данные можно передать отдельно в CSV с колонками **sku,month,days_out**, например:

    sku,month,days_out
    200400085,2026-08,5

Загрузка stockout CSV используется для текущего расчёта и не сохраняется сервером.

## Ограничения текущей версии

- В исходных выгрузках нет обезличенного **client_id**; выявление разовых продаж выполняется по документу и SKU, без группировки продаж одного клиента.
- История stockout не передана поставщиками. Поправка применяется только если пользователь задаёт её в сценарии или загружает CSV.
- В источниках нет сроков поставки. Пользовательский горизонт — настраиваемое допущение, а не фактический lead time.
- В журнале продаж нет цены; система не оценивает закупку в денежном выражении.
- Для IEK не передана категория товара; для отсутствующего в отчёте MOQ используется 1 единица.
- Остатки относятся к разным датам: IEK — начало сентября 2026 года, Systeme Electric — свободный остаток из отчёта на 22.09.2026.
- Точность прогноза не оценивалась на отдельной отложенной выборке; рекомендации нужно проверять закупщику.
- Нет учётных записей пользователей, общей базы данных и автоматической отправки заказа поставщику.
- CSV — обычная выгрузка списка рекомендаций; совместимость с конкретным импортным форматом 1С не подтверждена.
